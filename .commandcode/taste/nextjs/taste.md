# Next.js

- Prefers `next start` (non-standalone) over `output: "standalone"` for Docker/production deployments — expects the Dockerfile to install production `node_modules` via `npm ci --omit=dev`, copy the full `.next` directory, and use `CMD ["npx", "next", "start"]` rather than running `node server.js` from a standalone build. Confidence: 0.8
- Guards browser-only APIs (e.g., `document.cookie`) with `typeof document === "undefined"` checks for SSR safety in Next.js — server-side code must never assume DOM availability. Confidence: 0.8
- Prefers a two-layer page structure in Next.js App Router: a thin server component (`page.tsx`) that handles server-only concerns (metadata, title, server-side data fetching) and delegates to a sibling Client Component (e.g., `page-client.tsx` or `page-content.tsx`) that contains all hooks (`useRouter`, `useLogin`, etc.), form logic, and interactivity. Confidence: 0.9
- Prefers placing `"use client"` directives only at the boundary component (e.g., `page-client.tsx`) — child components automatically inherit the client context and do not need their own directive. Avoids redundant directives on components that are already imported by a client component. Confidence: 0.7
- Composes navigation links with button styling via `<Button render={<Link href="..." />} nativeButton={false}>` rather than styling `<Link>` directly as a button or using `asChild`-style patterns. Confidence: 0.7
- Prefers deriving protected-route config from the folder structure (scanning the `(authenticated)` route group to generate the protected-routes list) rather than maintaining a hardcoded `protectedRoutes` array — treats the route-group folder as the single source of truth for auth protection (convention over hardcoded config). Confidence: 0.7
- Prefers plural resource route segments (e.g., `/campaigns` over `/campaign`). Confidence: 0.5
- Organizes top-level app-shell components into dedicated `app-*` folders (e.g., `app-topbar/`) and names the wrapper component with a `-layout` suffix (e.g., `app-topbar-layout.tsx`), rather than a generic `layout/` folder. Confidence: 0.5
- Prefers moving server-side auth cookie reads (e.g., deriving `hasAccessToken` from the access-token cookie) out of `page.tsx` and into a dedicated async server layout component (e.g., `app-topbar-layout.tsx`), so pages stay free of server-only cookie logic. Confidence: 0.6
- Prefers applying a shared app shell through a Next.js route-group `layout.tsx` (e.g., `src/app/(home)/layout.tsx`) that delegates to the dedicated layout component, rather than wrapping each page manually or relying on a standalone wrapper alone. Confidence: 0.7
- Prefers extracting self-contained UI blocks (e.g., the avatar dropdown, guest login/register actions) into their own colocated component files (`avatar-dropdown.tsx`, `guest-actions.tsx`) rather than leaving them inline in a growing parent component; explicitly directs that when a component is genuinely needed, it should live in its own new file (and only extract when it's really warranted, not gratuitously). Confidence: 0.8
- Prefers the app sidebar navigation to be declaratively configured as typed data (e.g., `NAV_ROUTES: TNavSidebar[]`) and rendered generically, with a per-item `variant` flag to switch between a collapsible group and a labeled `SidebarGroup` — rather than hand-coding each group's JSX; extends this config to support nested (2nd-level) groups. Confidence: 0.7
- Prefers rendering items driven by a config/data array in the exact order they are defined in that source, rather than reordering or grouping them by type/variant/category first (e.g., iterating `NAV_ROUTES` once in order instead of splitting into `menuItems` and `labelItems`). Confidence: 0.7
- Prefers building new admin pages by mirroring an existing reference page's list structure rather than designing a bespoke layout — e.g., `/dashboard/iam/permission` should be "just a list" modeled after `/dashboard/requestors/audit-logs`. Confidence: 0.6
- Prefers card-based list layouts (responsive grid with Avatar, Badge, stats) over DataTable for entity pages that feature rich visual information — explicitly requested cards instead of a table for the IAM users page while keeping the same search/pagination/URL-state patterns. Tables are reserved for denser, more tabular data (e.g., roles, audit logs). Confidence: 0.7
- Names colocated type files after the specific view component they serve rather than a generic `table` or bare entity name — e.g., `user-card-list-sort-by.ts` for a card-list view's sort type, not `user-table-sort-by.ts` or `user-sort-by.ts`. The filename should accurately reflect the UI component it backs. Confidence: 0.8
- Prefers searchable comboboxes with server-side search (hitting the API endpoint on each query) over preloading bulk data (e.g., fetching 100 items into a plain Select) for filter/reference dropdowns — values lazy, search-driven data fetching for potentially large datasets rather than eager bulk loading. Confidence: 0.9
