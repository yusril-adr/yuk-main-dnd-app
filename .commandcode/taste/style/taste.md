# Style

- Prefers single-responsibility utilities — each module should do one thing (e.g., separate `AccessToken` for localStorage and `HasTokenCookie` for cookies), with callers importing and calling both independently rather than one utility mixing concerns. Confidence: 0.8
- Prefers explanatory comments above non-obvious patterns or workarounds (e.g., `next-themes` hydration guard, SSR safety checks, `useRef` for stale-closure avoidance) so other developers understand the "why" without having to reverse-engineer the fix. Confidence: 0.9
- Prefers the project's UI component primitives (e.g., `<Button variant="ghost" size="icon-sm">`) over raw utility classes like `btn btn-ghost btn-square btn-sm` — uses the design system's props API rather than ad-hoc class composition. Confidence: 0.7
- Treats shadcn/ui generated components (under `_components/ui/`) as immutable — do not edit them to fix warnings or runtime issues. Instead, suppress the issue or work around it at the call site. This is a deliberate exception to the general preference for root-cause fixes; generated design-system code should remain untouched. Confidence: 0.9
- Prefers to add shadcn/ui components himself (e.g., via the shadcn CLI) and does not want the agent to create or update any file under `src/app/_components/ui` — when a UI primitive is needed, expect it may already exist and use it as-is rather than scaffolding or modifying one. Confidence: 0.8
- Prefers ui-avatars.com-generated avatar images for user profile pictures (e.g., `https://ui-avatars.com/api/?background=random&name={name}`). Confidence: 0.7
- Prefers responsive topbar navigation that collapses to a hamburger menu on mobile/tablet (below `lg`), showing only logo + title + hamburger and opening a right-side drawer (Sheet) containing the nav links and auth actions, while keeping the full inline nav at `lg` and up. Confidence: 0.8
- Prefers mirroring existing in-app component patterns for consistency — when asked to replicate a feature across components (e.g., "add stats and profile in avatar sidebar like in topbar"), expects the existing implementation to be mirrored directly rather than reinvented. Confidence: 0.6
- Prefers TypeScript string enums over union string literal types for variant/flag fields — when a type declares a `variant` as a string union, converts it to an enum (e.g., `NavSidebarVariantEnum`), storing feature-specific enums in a feature-local `_enums/` directory (e.g., `dashboard/_enums/nav-sidebar-variant.ts`) rather than a global `src/common/enums/`. Confidence: 0.7
- Prefers TypeScript enums named with a `Enum` suffix (e.g., `PermissionEnum`, `RoleKeyEnum`, `AuditLogActionEnum`) rather than a bare name like `Permission`. Confidence: 0.8
- Prefers TypeScript types to use a `T` prefix (e.g., `TUserSortBy`, `TUserTableSortBy`, `TRoleTableSortBy`) — a naming convention analogous to the `Enum` suffix for enums. Confidence: 0.8
- Stores feature-specific TypeScript types in a feature-local `_types/` directory (e.g., `users/_types/user-sort-by.ts`), mirroring the existing `_enums/` directory convention — narrow types are derived from broader API types using utility types like `Extract` or `Exclude`. Confidence: 0.8
- Expects type and file names to be semantically accurate to their actual scope — don't include domain qualifiers (like "table") in names if the type isn't specifically tied to that concept. If a sort-by type is used beyond table contexts, name it `TUserSortBy` / `user-sort-by.ts`, not `TUserTableSortBy` / `user-table-sort-by.ts`. Confidence: 0.8
- Prefers lowercase string enum values (e.g., `"admin"`, `"create"`, `"events:read"`) rather than UPPER_CASE or PascalCase values. Confidence: 0.7
- Prefers `react-if` (`<If condition>` / `<Then>` / `<Else>`) for conditional rendering in React components over ternaries — proactively scans the codebase to eliminate ternaries and enforce this pattern project-wide. Confidence: 0.9
- Expects skeleton/loading-state components to mirror the exact layout of the actual component they replace (same CardHeader/CardContent/CardFooter structure, same grid, same flex containers, same spacing) — skeleton mismatch that causes layout shift on load is a bug to fix. Confidence: 0.8
- Prefers fantasy/RPG-themed UI design elements (e.g., "adventure guild paper" card with ornamental text like "♦ Guild Record ♦", decorative separators, parchment-style cards) for D&D app detail/profile pages, but explicitly keeps it minimalist — thematic flourishes should be subtle (faint borders, small ornaments, muted accent colors) rather than heavy or ornate. Confidence: 0.8
- Prefers large, centered avatars (e.g., h-28 w-28) on user detail/profile pages, with a subtle halo/ring accent — rather than small inline avatars next to text. Confidence: 0.8
- Prefers centered, narrow card layouts (e.g., max-w-lg) for single-entity detail/profile views rather than full-width tables — groups info vertically in a compact, readable format. Confidence: 0.8
